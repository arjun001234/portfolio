EKS 1.34 end of standard support: a zero-downtime upgrade playbook

On 2 December 2026, every EKS cluster still on Kubernetes 1.34 moves into extended support and starts costing six times as much for its control plane. That's the easy part to fix. The harder part is getting from 1.34 to 1.36 or 1.37 without an outage, when there are three versions' worth of changes between you and a supported release. This is the playbook I'd follow.

Kubernetes ships three minor releases a year, and Amazon EKS supports each one for 14 months of standard support plus 12 months of paid extended support. That cadence means a platform team is never more than a few months away from its next forced decision. This month, two of those decisions land at once: EKS 1.31 reaches the end of extended support on 26 November, and 1.34 leaves standard support on 2 December.

I upgraded EKS from 1.33 to 1.36 at work this year, over about two months. The biggest lesson wasn't any single breaking change. It was that upgrades go smoothly when they're a repeatable process with checks at each step, and painfully when they're a yearly event someone has to rediscover. This post is that process, written for anyone with a 1.34 cluster and two weeks.

1. The dates that matter this month

Here's the current state of the EKS Kubernetes version calendar, as of today:

VersionEnd of standard supportEnd of extended supportWhat happens next
1.3126 Nov 202526 Nov 2026EKS upgrades the control plane to 1.32 for you, at a time it doesn't announce. Nodes and add-ons stay where they are.
1.3223 Mar 202623 Mar 2027Already in extended support and already paying for it.
1.3329 Jul 202629 Jul 2027Same as 1.32.
1.342 Dec 20262 Dec 2027Moves to extended support and the higher price, unless the upgrade policy says otherwise.
1.3527 Mar 202727 Mar 2028A short-lived target. You'd be doing this again in four months.
1.362 Aug 20272 Aug 2028A sensible target if you want proven add-on versions.
1.371 Dec 20271 Dec 2028The newest. A full year of standard support from here.

One detail in the AWS docs deserves attention: when EKS performs a forced upgrade at the end of a support window, it only upgrades the control plane. Self-managed nodes and managed node groups stay on the old version, and add-ons aren't touched. You end up with exactly the version skew you'd normally plan carefully, created at a time you didn't pick.

2. What extended support actually costs

The EKS pricing page lists $0.10 per cluster-hour in standard support and $0.60 in extended support. Fifty cents an hour sounds like nothing, which is why it gets ignored. It adds up across a fleet:

Clusters on extended supportExtra cost per monthExtra cost per yearRough comparison
1$365$4,380A small production node group
5 (dev, staging, prod in a few regions)$1,825$21,900A good engineer's time for a few weeks
20 (multi-tenant or per-customer clusters)$7,300$87,600A real line item a finance team will ask about

These numbers use 730 hours a month and only count the extra $0.50. The control-plane fee is the visible part. The cost that doesn't show up on the bill is risk: on extended support you still get security patches for the control plane, but the community and the add-on ecosystem move on. Helm charts, operators and controllers drop old versions from their test matrices first. The FinOps Foundation framework would file this under avoidable spend, and that's the right frame: extended support is a bridge you pay for on purpose, not a place to live.

Extended support is the right call when the upgrade can't be done safely before the deadline. It's the wrong call when it's chosen by default because nobody looked at the date. The policy switch in the next section makes that choice explicit.

3. The upgrade policy is a decision, not a default

Every EKS cluster has an upgrade policy with a supportType of EXTENDED or STANDARD. It defaults to EXTENDED. With STANDARD, the cluster never enters extended support. Instead, EKS upgrades the control plane automatically when standard support ends. So the real choice is between paying more and having the control plane upgraded underneath you. Neither is a plan, which is why the policy should be set deliberately, per environment, in code:

# Terraform, AWS provider 5.x / 6.x
resource "aws_eks_cluster" "this" {
  name     = var.cluster_name
  version  = var.kubernetes_version          # bumped one minor at a time, through a merge request
  role_arn = aws_iam_role.cluster.arn

  upgrade_policy {
    # dev and staging: STANDARD, so a forgotten cluster gets upgraded, not billed
    # production: EXTENDED, so a hard deadline never forces an unplanned control-plane upgrade
    support_type = var.environment == "prod" ? "EXTENDED" : "STANDARD"
  }

  vpc_config {
    subnet_ids = var.private_subnet_ids
  }
}

That split reflects a trade-off I'd make on most platforms. In non-production, an automatic upgrade is a cheap early warning: if something breaks there, you'd rather find out on a Tuesday than in production. In production, I'd keep EXTENDED as insurance and treat any month spent in it as an incident-style signal that the upgrade process is too slow. To see where a fleet stands today:

# Version and support policy for every cluster in a region
for c in $(aws eks list-clusters --query 'clusters[]' --output text); do
  aws eks describe-cluster --name "$c" \
    --query 'cluster.[name, version, upgradePolicy.supportType]' --output text
done

# Opt a non-production cluster out of extended support
aws eks update-cluster-config --name dev-apps --upgrade-policy supportType=STANDARD

4. In-place or blue/green?

There are two industry-standard ways to upgrade a cluster, and the EKS Best Practices Guide covers both. In-place upgrades the existing cluster one minor version at a time: control plane, then add-ons, then nodes. Blue/green builds a new cluster on the target version, moves workloads and traffic across, and deletes the old one. EKS only lets you move the control plane up one minor version per upgrade, so going from 1.34 to 1.37 in place means three full hops. Blue/green can jump straight there.

In-placeBlue/green cluster
Hops from 1.34 to 1.37Three control-plane upgrades, with add-ons and nodes after eachOne build, one migration
RollbackControl plane can't be downgraded; you roll forward or roll back workloads and nodesShift traffic back to the old cluster
Extra costNone beyond surge nodesTwo clusters' worth of nodes during the overlap
What it needsGood PDBs, add-on discipline, patienceEverything in Git, external state, a traffic-shifting layer, IAM and DNS that aren't tied to one cluster
Hidden workRepeated checks per hopPod Identity associations, IRSA trust policies, security groups, allowlisted egress IPs, webhooks and certificates for the new cluster
Best forOne or two versions behind, stateful or tightly integrated clustersFar behind, or bundling a big platform change into the move

My default is in-place for clusters that are close to current, and blue/green when a cluster has drifted a long way or needs a foundational change anyway. The deciding question is how portable your workloads really are. If deploying a fresh cluster from Git is something you do monthly, blue/green is low risk. If it's something you've never tried, the upgrade is the wrong time to find out.

5. What changed between 1.34 and 1.37

Each minor release has its own release notes and "urgent upgrade notes", and you should read all three sets for 1.35, 1.36 and 1.37. These are the changes I'd check first, because they fail at the node or workload level rather than showing up as an API warning:

For the two workload-level items, these queries find offenders in a running cluster:

# Pods that use the gitRepo volume type (won't run on 1.36+ kubelets)
kubectl get pods -A -o json | jq -r '.items[]
  | select(any(.spec.volumes[]?; has("gitRepo")))
  | "\(.metadata.namespace)/\(.metadata.name)"'

# Services that still set externalIPs (deprecated in 1.36)
kubectl get svc -A -o json | jq -r '.items[]
  | select(.spec.externalIPs != null)
  | "\(.metadata.namespace)/\(.metadata.name) \(.spec.externalIPs | join(","))"'

# kube-proxy mode on EKS ("" or "iptables" is fine, "ipvs" needs a plan)
kubectl -n kube-system get configmap kube-proxy-config -o yaml | grep -E '^\s*mode:'

6. Pre-flight checks

The best-known public example of an upgrade going wrong is Reddit's Pi Day outage in March 2023. An in-place upgrade from 1.23 to 1.24 removed an old node label that their Calico route reflector configuration still selected on, and pod networking fell apart across the cluster. Nothing in Kubernetes was buggy. A dependency around it relied on something that changed. That's the pattern the pre-flight is designed to catch: an add-on that doesn't support the new version, a webhook that times out, a label or API something still depends on. Find those before the control plane moves, because it can't move back.

EKS upgrade insights

EKS cluster insights scan the cluster's audit logs for calls to deprecated APIs and check things like kubelet version skew and add-on compatibility for the next version. They're free and already running. Make reading them a required step:

# Anything that isn't PASSING blocks the hop
aws eks list-insights --cluster-name prod-apps \
  --filter '{"categories":["UPGRADE_READINESS"],"statuses":["ERROR","WARNING","UNKNOWN"]}' \
  --query 'insights[].[name, insightStatus.status, kubernetesVersion]' --output table

# Details, including which clients called a deprecated API and when
aws eks describe-insight --cluster-name prod-apps --id <insight-id>

# Add-on versions that support the next minor version
for a in vpc-cni coredns kube-proxy aws-ebs-csi-driver eks-pod-identity-agent; do
  aws eks describe-addon-versions --addon-name "$a" --kubernetes-version 1.35 \
    --query 'addons[0].addonVersions[0].addonVersion' --output text | sed "s/^/$a: /"
done

Insights only see API calls that actually happened during their lookback window. A CronJob that runs monthly, or a Helm chart that's only applied on release day, won't show up. So I'd also scan the source of truth: run a tool like Pluto against the rendered manifests in the GitOps repo, not just the live cluster.

The things outside Kubernetes

  • Controllers and operators. Karpenter, the AWS Load Balancer Controller, cert-manager, External Secrets, Argo CD, KEDA, service meshes and database operators all publish support matrices. Upgrade them to a version that supports both the current and the target Kubernetes version before the hop.
  • Admission webhooks. List every ValidatingWebhookConfiguration and MutatingWebhookConfiguration. A webhook with failurePolicy: Fail whose backend is unhealthy can block every pod creation during node rotation.
  • IaC and CI. Pin the new version in Terraform first, and make sure the pipeline's kubectl and Helm versions are within the supported skew.
  • The stateful tier. Databases and brokers running on EC2 aren't upgraded by EKS, but their clients and any operators in the cluster are. Check client library and operator compatibility, not just the server.

7. The upgrade sequence, one hop at a time

The Google SRE book's chapter on release engineering argues for releases that are repeatable and boring. A cluster upgrade fits that perfectly once it's broken into the same five steps every time, with a gate between each:

A few rules make the loop safe:

  • Lowest environment first, every hop. Dev goes 1.34 → 1.35, then staging, then production, before anyone starts 1.35 → 1.36. Running hops in parallel across environments removes the point of having environments.
  • Add-ons right after the control plane. AWS publishes a default add-on version for each Kubernetes version. Leaving CoreDNS or the VPC CNI several versions behind is how skew bugs sneak in.
  • Don't stack node rotations. With kubelets allowed to be up to three minor versions behind the API server, it's tempting to upgrade the control plane three times and rotate nodes once. It works, but it puts three versions of change into one node rollout and makes any failure much harder to pin down. I'd rotate nodes on every hop.
  • Soak for at least a day. Some failures, like a controller that only reconciles on a timer or a CronJob that runs at night, take a while to appear.

8. Rotating nodes without dropping traffic

The control-plane step is the scary one, but the node rotation is where users actually feel an upgrade. Every pod gets evicted and rescheduled, so this step is only as safe as your PodDisruptionBudgets, readiness probes and graceful shutdown handling.

With Karpenter, the clean way to do it is drift. If the EC2NodeClass selects the EKS-optimised AMI by alias, Karpenter resolves the AMI for the cluster's current Kubernetes version. After the control plane moves, the resolved AMI changes, existing nodes are marked as drifted, and Karpenter replaces them. Disruption budgets control the pace:

apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: general
spec:
  role: KarpenterNodeRole-prod-apps
  amiSelectorTerms:
    - alias: al2023@v20261101        # example version: pin in prod, bump through Git so drift happens when you choose
  subnetSelectorTerms:
    - tags: { karpenter.sh/discovery: prod-apps }
  securityGroupSelectorTerms:
    - tags: { karpenter.sh/discovery: prod-apps }
  metadataOptions:
    httpTokens: required
    httpPutResponseHopLimit: 1
---
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: general }
      expireAfter: 720h
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    budgets:
      - nodes: "10%"                 # at most 10% of nodes disrupted at once, for any reason
      - nodes: "0"                   # no drift replacements 03:00-17:00 UTC (daytime in India and Europe)
        reasons: [Drifted]
        schedule: "0 3 * * *"
        duration: 14h

Pinning the alias in production is a deliberate choice. With al2023@latest, nodes drift whenever AWS publishes a new AMI, which is convenient in dev and surprising in production. Pinned, the AMI bump is a merge request you schedule right after the control-plane hop.

On the workload side, every Deployment that serves traffic needs a PDB that allows some disruption, plus enough replicas spread across zones for the PDB to mean something:

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: checkout-api
spec:
  maxUnavailable: 1                   # not minAvailable: 100%, which blocks every drain
  unhealthyPodEvictionPolicy: AlwaysAllow   # don't let crash-looping pods block node rotation
  selector:
    matchLabels: { app: checkout-api }

Two PDB mistakes cause most stuck rotations: a budget that allows zero disruptions (often a single-replica Deployment with minAvailable: 1), and a budget whose selector matches nothing. Find both before the hop, with a quick look at kubectl get pdb -A for any row where ALLOWED DISRUPTIONS is 0. Also make sure pods shut down cleanly: a preStop sleep a little longer than your load balancer's deregistration delay avoids the burst of 502s that often shows up during rotations behind an ALB.

9. Failure modes and what rollback really means

An EKS control plane can't be downgraded. That changes what "rollback" means: you can roll back workloads, add-ons and node AMIs, but past the control-plane step the only way out is forward. This is why the pre-flight gate matters so much, and why blue/green is attractive for big jumps. These are the failures worth rehearsing:

SymptomLikely causeMitigation
New nodes never become Readycgroup v1 image on 1.35+, AMI not matching the version, or a CNI add-on too oldStop the rollout (Karpenter budget to 0 or pause the node group update); fix the AMI or add-on; old nodes keep serving
Node drain stuck for hoursPDB with zero allowed disruptions; pods without controllersFix the PDB; scale the workload up; use terminationGracePeriod on the NodePool as a ceiling
Pods fail to create after the hopAdmission webhook down or incompatible; a removed API in a chartFix or temporarily scope the webhook; roll back the chart to a working version
Intermittent DNS failuresCoreDNS version skew or too few replicas during rotationUpgrade the CoreDNS add-on; set a PDB and anti-affinity on CoreDNS
GitOps sync suddenly failingStricter validation in 1.36 rejecting an old IP or CIDR valueFix the value in Git; validation ratcheting keeps existing objects running
5xx burst during rotationNo graceful shutdown; load balancer still sending to terminating podspreStop delay, readiness gates, and drift during low traffic only

The AWS Well-Architected Reliability Pillar recommends automating changes and testing them in a production-like environment first. For upgrades, that means the staging cluster has to be a real rehearsal: same add-ons, same controllers, same webhooks and the same PDBs as production. A staging cluster that's missing half of production's add-ons can pass a hop that production then fails.

10. A two-week plan and checklist

If you have 1.34 clusters today, two weeks is enough for one careful hop to 1.35 in production, which is enough to stay in standard support until March. That buys time to do 1.36 and 1.37 properly instead of in a rush. Here's how I'd lay it out:

  1. Day 1: inventory and decide. List every cluster with its version and supportType. Set non-production to STANDARD. Decide in-place or blue/green per cluster, and write down the target version.
  2. Days 2–3: pre-flight. Read the 1.35 urgent upgrade notes. Clear every non-passing upgrade insight. Run the gitRepo, externalIPs, kube-proxy and cgroup checks. Upgrade controllers to versions that support both 1.34 and 1.35.
  3. Days 4–5: dev. Run the full loop in dev, including node rotation. Note anything that needed a manual step and automate it.
  4. Days 6–8: staging. Same loop, with a load test running during node rotation so you see what users would see. Soak for a day.
  5. Days 9–11: production. Upgrade during low traffic, with the on-call engineer aware. Rotate nodes under disruption budgets. Watch SLOs and error budget burn.
  6. Days 12–14: buffer, then start 1.36. Keep two days for surprises. Then start the next hop's pre-flight, so the next deadline is never a deadline.

And the checklist I'd run before every hop:

  1. The target version and the upgrade policy are set in Terraform, through a merge request.
  2. EKS upgrade insights show nothing in ERROR, WARNING or UNKNOWN.
  3. Rendered manifests from Git have been scanned for removed APIs, not just the live cluster.
  4. Every controller, operator and webhook has a version that supports the target Kubernetes version.
  5. Node images are on cgroup v2, and none of them are AL2.
  6. No pods use gitRepo volumes; externalIPs users have a migration plan.
  7. Every serving workload has at least two replicas and a PDB that allows one disruption.
  8. Karpenter disruption budgets and a schedule window are set; managed node groups have a sensible max-unavailable.
  9. Pods shut down gracefully behind the load balancer.
  10. Staging has the same add-ons, controllers and webhooks as production and has already done this hop.
  11. SLO dashboards and a rollback plan for workloads and nodes are ready. Everyone knows the control plane only goes forward.
  12. The next hop's date is in the calendar before this one is closed.

The short version

EKS 1.34 leaves standard support on 2 December 2026. Staying put costs $0.50 more per cluster-hour, and switching the policy to STANDARD just means EKS upgrades the control plane for you. Neither is a plan. The plan is a repeatable loop: pre-flight, control plane, add-ons, nodes, verify, one minor version at a time, lowest environment first, with disruption budgets doing the hard work during node rotation. Make it boring enough that you do it three times a year, and these deadlines stop being events.
