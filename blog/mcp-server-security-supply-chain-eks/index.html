MCP servers are supply chain: securing the agent tool layer on EKS

More than ten MCP CVEs have been published this year, and almost none of them are new kinds of bug. They're SSRF, injection, skipped authorization checks and tokens accepted by the wrong service, sitting in a layer most platform teams haven't inventoried yet. This is how I'd treat MCP servers on EKS: as dependencies with an owner, a pinned version, a narrow identity and a short leash on the network.

A year ago, MCP servers were something a developer added to their IDE on a Friday afternoon. Now they sit between AI agents and real systems: Kubernetes clusters, cloud accounts, ticketing tools, Git hosting and databases. Every one of them is a piece of third-party code holding a credential, receiving input shaped by a language model, and making network calls on someone's behalf.

That's the definition of a supply chain dependency, and the 2026 vulnerability record treats it that way. Newly's 2026 MCP server CVE roundup, published on 26 October, counts more than ten flaws in MCP servers and tooling this year, including one in a Kubernetes MCP server scored 9.3 that could leak the operator's bearer token. The MCP Inspector project published nine advisories on 21 October alone. None of the roundup's entries have confirmed in-the-wild exploitation, which is exactly why now is the time to fix the platform side, before they do.

I use AI agents at work to write and maintain Terraform, and I spent part of this year moving our container images to ECR with scan-on-push and working through CISA KEV fixes. So I tend to look at MCP through those two lenses: what can the agent reach, and how do I know what code is running. This post is the design I'd propose for an EKS platform team.

1. Why MCP is a supply chain problem

The Model Context Protocol is a simple idea: a client (the agent or IDE) discovers tools on a server and calls them with JSON arguments. The simplicity is the point, and it's also why the risk is easy to underestimate. Three things make an MCP server different from an ordinary library:

  • It holds credentials the agent doesn't. The server is where the GitLab token, the kubeconfig or the AWS role lives. Compromise the server and you have the credential, not just the agent's session.
  • Its input is attacker-influenced by design. Tool arguments are written by a model that has read issues, logs, web pages and documents. Any of those can carry instructions. So every argument is untrusted input, exactly like a form field on a public website.
  • Its descriptions are part of the prompt. Tool names and descriptions go straight into the model's context. A server update that changes a description can change agent behaviour without changing a line of your code. That's the "tool poisoning" class in the OWASP MCP Top 10.

The industry already knows how to handle code like this. SLSA covers build provenance, NIST SP 800-218 (SSDF) covers secure development and dependency practice, and the AWS Well-Architected Security Pillar covers least-privilege identity and network controls. The work is applying them to a layer that grew up outside the platform.

2. What the 2026 CVEs have in common

Reading the roundup as a platform engineer rather than a security researcher, the useful exercise is to group the flaws by root cause and ask which platform control would have limited each one. Patching is necessary, but the next CVE will be in a server you haven't heard of yet. Controls are what carry over.

Two patterns jump out. First, most of these are classic web bugs. The OWASP SSRF cheat sheet applies without changes. Second, the impact of nearly every one depends on what the server's identity and network allow. A server with a read-only role and no route to the internet turns a 9.x into an annoyance. That's where the platform team has the most leverage.

3. A gateway in front of every tool

The pattern the industry is converging on is an MCP gateway: one place where agents connect, which authenticates them, decides which tools each one may call, applies policy to arguments, and writes an audit record. Open-source options include agentgateway (which runs on Kubernetes with kgateway), and several API gateways have added MCP support. Behind the gateway, servers run in their own namespace with their own identities.

The design choices that matter:

  • One server per upstream system, one identity per server. A "do everything" server with an admin token is the MCP version of running every microservice as root. Small servers with narrow roles keep each CVE's blast radius small.
  • Agents never talk to servers directly. NetworkPolicy allows ingress to the mcp-servers namespace only from the gateway. That gives you one place for authentication, policy and audit, and one place to switch a server off.
  • The registry is the source of truth. Which servers are approved, at which image digest, exposing which tools with which definition hashes. The gateway enforces it; a merge request changes it.

4. Tokens that mean one thing

The current MCP specification (version 2026-07-28) is clear about tokens, and most of the authorization bugs this year come from ignoring it. An HTTP MCP server acts as an OAuth 2.1 resource server. Clients must send a resource parameter (RFC 8707) naming the server they want a token for. Servers must validate that the token was issued for them, and the spec says servers "MUST NOT accept or transit any other tokens". The security best practices page calls forwarding a client's token downstream "token passthrough" and forbids it. The 2026-07-28 revision also deprecated Dynamic Client Registration in favour of Client ID Metadata Documents, and made the protocol stateless, so servers shouldn't treat a state handle as proof of identity.

In platform terms, that means three different credentials in one tool call, each with exactly one audience:

The server's cloud identity is the layer platform teams own outright, and it's where I'd spend effort first, because it caps the damage from every authorization bug in section 2. On EKS, EKS Pod Identity gives each server's ServiceAccount its own IAM role without node-level credentials. Here's a read-only CloudWatch role in Terraform:

# One role per MCP server. Pod Identity adds session tags (namespace, service account, cluster).
resource "aws_iam_role" "mcp_cloudwatch_ro" {
  name = "mcp-cloudwatch-readonly"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "pods.eks.amazonaws.com" }
      Action    = ["sts:AssumeRole", "sts:TagSession"]
    }]
  })
}

resource "aws_iam_role_policy" "mcp_cloudwatch_ro" {
  role = aws_iam_role.mcp_cloudwatch_ro.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid      = "QueryAppLogsOnly"
        Effect   = "Allow"
        Action   = ["logs:StartQuery", "logs:FilterLogEvents", "logs:DescribeLogStreams"]
        Resource = "arn:aws:logs:ap-south-1:123456789012:log-group:/app/*"   # not audit or security log groups
      },
      {
        Sid      = "ReadQueryResultsAndMetrics"
        Effect   = "Allow"
        Action   = ["logs:GetQueryResults", "cloudwatch:GetMetricData", "cloudwatch:ListMetrics"]
        Resource = "*"                                   # these actions don't support resource scoping
      }
    ]
  })
}

resource "aws_eks_pod_identity_association" "mcp_cloudwatch_ro" {
  cluster_name    = var.cluster_name
  namespace       = "mcp-servers"
  service_account = "mcp-cloudwatch"
  role_arn        = aws_iam_role.mcp_cloudwatch_ro.arn
}

Two habits make this hold up over time. Keep the role scoped to the log groups the server actually needs, so a prompt-injected "show me the CloudTrail logs" fails at IAM rather than relying on the model to behave. And manage these roles in the same Terraform modules, with the same drift detection, as the rest of the platform. An MCP role created by hand in the console is the one nobody reviews.

5. Signed, pinned and boring images

Most MCP servers are distributed as npm or PyPI packages and started with npx or uvx. That's convenient on a laptop and a problem in a cluster: the version is resolved at start-up, the package's install scripts run with the server's privileges, and two replicas can end up running different code. The fix is the same thing we did for application images: build once in CI, pin dependencies with a lockfile, produce an SBOM, sign the image, push it to your own ECR with scan-on-push, and deploy by digest.

Admission control then makes it a rule instead of a habit. With Kyverno's image verification, pods in the MCP namespace only start if the image is signed by your CI pipeline, and tags get rewritten to digests:

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: mcp-servers-signed-images
spec:
  webhookTimeoutSeconds: 30
  rules:
    - name: verify-ci-signature
      match:
        any:
          - resources:
              kinds: [Pod]
              namespaces: [mcp-servers]
      verifyImages:
        - imageReferences:
            - "123456789012.dkr.ecr.ap-south-1.amazonaws.com/mcp/*"
          failureAction: Enforce
          mutateDigest: true          # tag in, digest out
          verifyDigest: true
          required: true
          attestors:
            - entries:
                - keyless:            # Sigstore keyless signature from the CI job's OIDC identity
                    issuer: "https://gitlab.example.com"
                    subject: "https://gitlab.example.com/platform/mcp-servers//.gitlab-ci.yml@refs/heads/main"
                    rekor:
                      url: https://rekor.sigstore.dev

If you'd rather stay AWS-native, AWS Signer with Notation does the same job, and the Kyverno policy changes to a Notary attestor. Either way, the policy also needs an exception path for emergencies, documented and audited, or someone will turn the policy off at 2 AM.

The workload itself should look like the most locked-down service you run, because it's handling attacker-shaped input with a credential:

apiVersion: apps/v1
kind: Deployment
metadata: { name: mcp-cloudwatch, namespace: mcp-servers }
spec:
  replicas: 2
  selector: { matchLabels: { app: mcp-cloudwatch } }
  template:
    metadata:
      labels: { app: mcp-cloudwatch, mcp.example.com/tier: read-only }
    spec:
      serviceAccountName: mcp-cloudwatch
      automountServiceAccountToken: false   # no Kubernetes API access; Pod Identity mounts its own token
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: server
          image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/mcp/cloudwatch:1.4.2   # rewritten to @sha256 by Kyverno
          ports: [{ containerPort: 8080, name: mcp }]
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          resources:
            requests: { cpu: 100m, memory: 256Mi }
            limits: { memory: 512Mi }
          volumeMounts: [{ name: tmp, mountPath: /tmp }]
      volumes: [{ name: tmp, emptyDir: { sizeLimit: 64Mi } }]

Notice what's missing: no shell-heavy base image, no writable root, no capabilities and no Kubernetes token. The postgres COPY ... TO PROGRAM bug from the roundup is a reminder that "run an OS command" can hide inside a database feature, so the container should have as little as possible to run.

6. Egress is the blast radius

Look back at the SSRF and injection rows in the CVE table. In every case the attacker needs the server to reach somewhere it shouldn't: the instance metadata endpoint, an internal service, or a hostile API server. Default-deny egress turns those from credential theft into a failed connection and a log line.

Start with the cheap wins on EKS. Require IMDSv2 with a hop limit of 1 on your node groups and Karpenter EC2NodeClasses, so pods can't reach the node's metadata credentials at all. Then deny egress by default in the mcp-servers namespace. The Amazon VPC CNI enforces standard Kubernetes NetworkPolicy, which works with IPs and CIDRs. Most MCP servers talk to SaaS APIs by hostname, though, so FQDN rules are far easier to keep correct. With Cilium that looks like this:

apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: mcp-gitlab-egress
  namespace: mcp-servers
spec:
  endpointSelector:
    matchLabels: { app: mcp-gitlab }
  egress:
    - toEndpoints:                      # DNS, inspected so toFQDNs can learn the IPs
        - matchLabels:
            "k8s:io.kubernetes.pod.namespace": kube-system
            "k8s:k8s-app": kube-dns
      toPorts:
        - ports: [{ port: "53", protocol: ANY }]
          rules:
            dns: [{ matchPattern: "*" }]
    - toFQDNs:                          # the one upstream this server exists for
        - matchName: gitlab.example.com
      toPorts:
        - ports: [{ port: "443", protocol: TCP }]
# Anything not listed is dropped: no metadata endpoint, no cluster services, no internet.

If you're staying on the VPC CNI only, the common alternative is an egress proxy that enforces a hostname allowlist and blocks private ranges. Stripe's Smokescreen is the example the MCP security page itself points to. Also deny ingress to the namespace from everything except the gateway, so a compromised agent pod elsewhere in the cluster can't call servers directly.

A useful test for every MCP server: if its process were fully compromised right now, what's the worst thing its role and its network policy would let an attacker do? If the answer is longer than one sentence, the server is too powerful.

7. Tool definitions drift, and that's an attack

Image signing proves which code is running. It doesn't tell you that the tool called search_issues still has the description you reviewed. Some servers build tool lists dynamically, and a version bump can change descriptions, add parameters, or add a new tool entirely. Since descriptions go straight into the model's context, a changed description is a changed prompt. This is how the "rug pull" pattern works: a server behaves well at review time and changes later.

The control is the same idea as a lockfile. When a server is approved, record a hash of each tool's name, description, input schema and annotations. Then check the live definitions against it at deploy time and on a schedule, and have the gateway refuse calls to any tool whose hash doesn't match:

# mcp_tool_lock.py: compare live tool definitions with the approved lock file
import hashlib, json, sys

FIELDS = ("name", "title", "description", "inputSchema", "outputSchema", "annotations")

def fingerprint(tool: dict) -> str:
    # Hash exactly what the model reads, in a canonical form
    material = {k: tool.get(k) for k in FIELDS}
    canonical = json.dumps(material, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()

def main(lock_path: str, live_path: str) -> int:
    with open(lock_path) as f:
        lock = json.load(f)                                  # {"tool_name": "sha256", ...}
    with open(live_path) as f:
        live = {t["name"]: fingerprint(t) for t in json.load(f)["tools"]}   # a tools/list result

    added = sorted(live.keys() - lock.keys())
    removed = sorted(lock.keys() - live.keys())
    changed = sorted(n for n in live.keys() & lock.keys() if live[n] != lock[n])

    for label, names in (("ADDED", added), ("REMOVED", removed), ("CHANGED", changed)):
        for name in names:
            print(f"{label}: {name}")
    return 1 if (added or changed) else 0                  # fail CI; a human re-reviews and updates the lock

if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))

The gateway then applies policy per call. Here's the shape of it in OPA's Rego: an agent may call a tool only if the registry lists it for that agent, the definition hash matches, and anything marked destructive has an approval. Note that the destructiveHint comes from the registry, where a human reviewed it, not from the server. MCP tool annotations are hints written by the server author, and a malicious server can simply claim everything is read-only.

package mcp.authz

import rego.v1

default allow := false

tool := data.registry.servers[input.tool.server].tools[input.tool.name]

known_tool if {
    input.tool.name in data.registry.agents[input.agent.id].allowed_tools
    input.tool.definition_sha256 == tool.sha256          # pinned at review time
}

destructive if tool.reviewed.destructive                  # reviewed by a human, not the server's own hint

allow if {
    known_tool
    not destructive
}

allow if {
    known_tool
    destructive
    input.approval.status == "approved"
    input.approval.approver != input.agent.owner         # no self-approval
}

The audit side completes the loop. The OpenTelemetry GenAI semantic conventions include attributes for agent and tool spans, such as gen_ai.agent.name and gen_ai.tool.name, so the gateway can emit one span per tool call with the agent identity, tool, decision and latency, and you can query it alongside the rest of your traces. OWASP lists "lack of audit and telemetry" as its own MCP risk for a reason: after an incident, the first question is always "what did the agent actually call?"

8. Local, self-hosted or vendor-hosted

Not every MCP server belongs in the cluster. The spec itself distinguishes STDIO servers, which run as a local process and take credentials from the environment, from HTTP servers that use OAuth. The question I'd ask first is whose credentials the server uses, because that decides where it can safely run.

9. The OWASP MCP Top 10 as platform controls

The OWASP MCP Top 10 is still in beta, but it's already a useful checklist because it names risks in a way security reviewers recognise. This is how I'd map each item to an owner and a control, so the list turns into backlog items instead of a slide:

Shadow servers (MCP09) deserve a special mention, because they're the one you can't fix with configuration. Developers will add servers to their IDEs because they're useful. The answer that works is the same as with shadow IT generally: make the approved path easier than the unapproved one, with a self-service way to request a new server and a turnaround measured in days, not quarters.

10. Runbook: the day an MCP CVE drops

Treat an MCP CVE like any other dependency vulnerability, with one difference: you also need to know which agents could reach the affected tools. If you have a registry and gateway audit logs, this takes an hour. Without them, it takes a week of asking around. This is the runbook I'd keep next to the registry:

StepActionDone when
1. ScopeQuery the registry and SBOMs for the affected package and version range. Check developer configs for local copies.A list of affected servers and owners
2. ContainDisable the affected tools at the gateway (a registry change), or scale the server to zero. Contain first, patch second.Calls to affected tools return a clear error
3. Assess exposureSearch gateway audit spans for calls to the affected tools since the vulnerable version was deployed. Check the server's role in CloudTrail for unusual calls.Evidence that it was or wasn't used
4. RotateIf exposure is possible, rotate the server's credentials: revoke tokens, rotate secrets. Pod Identity roles have no long-lived keys to rotate.Old credentials are invalid
5. PatchRebuild with the fixed version, re-sign, re-run the tool-definition check, deploy by digest.Fixed digest running, lock file updated
6. Re-enable and learnRe-enable tools. Ask which control limited the impact, and which one should have. Write it up blamelessly.Follow-up items in the backlog

For prioritisation, use the same sources as the rest of your vulnerability programme: the CISA KEV catalog for confirmed exploitation, EPSS for likelihood, and your own exposure data. A 9.3 in a server that can't reach anything is less urgent than a 6.8 in a server holding a write token to production.

11. A 30-day plan and checklist

You don't need a gateway product on day one to make real progress. This is the order I'd follow:

  1. Week 1: inventory. List every MCP server in use: in clusters, in CI, and in developer configs (ask, and scan). Record owner, version, credentials and upstream system. This is your first registry, even if it's a YAML file in Git.
  2. Week 2: identity and network. Move self-hosted servers into a dedicated namespace. Give each one its own Pod Identity role scoped to what it needs. Enforce IMDSv2 with hop limit 1, default-deny egress and ingress only from agents you know about.
  3. Week 3: supply chain. Build server images in CI with lockfiles and SBOMs, mirror to ECR with scan-on-push, sign them and enforce signatures in the namespace. Generate tool-definition lock files.
  4. Week 4: gateway and audit. Put a gateway in front, with audience checks, per-agent allowlists and one audit span per call. Add the drift check to CI and to a nightly job. Run the CVE runbook once as a tabletop exercise.

And the checklist I'd use in a design review for any new MCP server:

  1. The server is in the registry with an owner, a purpose and an upstream system.
  2. It talks to exactly one upstream system with its own narrowly scoped identity.
  3. Its role can't write unless writing is the point, and destructive tools need approval.
  4. It never receives or forwards a user's raw token; audiences are checked at every hop.
  5. The image is built in CI from a lockfile, scanned, signed and deployed by digest.
  6. It runs non-root with a read-only root filesystem, no capabilities and no Kubernetes token unless needed.
  7. Egress is default-deny, with an allowlist of the hostnames it needs; IMDS isn't reachable.
  8. Ingress is allowed only from the gateway.
  9. Tool definitions are hashed, and changes fail CI until a human re-reviews them.
  10. Every tool call produces an audit span with agent identity, tool, decision and result.
  11. The CVE runbook has been rehearsed, and disabling a tool is a one-line registry change.
  12. There's a fast, documented way for developers to get a new server approved.

The short version

MCP servers are code you didn't write, holding credentials you did issue, taking input from a model that reads untrusted text. That's a supply chain dependency, and the 2026 CVEs mostly show familiar bugs in an unfamiliar place. The fixes are familiar too: an inventory, one narrow identity per server, audience-bound tokens with no passthrough, signed and pinned images, default-deny egress, pinned tool definitions, and an audit trail you can query. Do those, and the next MCP CVE is a ticket, not an incident.
